# 開発ガイドライン：Stack Mankai

このドキュメントは、Stack Mankai プロジェクトの開発をスムーズかつ一貫性のあるものにするためのガイドラインを提供します。特に、過去に発生したエラーパターンを考慮し、不整合を未然に防ぐためのルールを明文化します。

## 1. 全般的なコーディング規約

*   **TypeScript の活用**: 型安全性を最大限に活用し、`any` の使用は最小限に抑えます。可能な限り明示的な型定義を行います。
*   **一貫性のある命名**: 変数、関数、コンポーネント、ファイル名には一貫性のある命名規則（例: camelCase, PascalCase, kebab-case）を適用します。
*   **コードの可読性**: 適切なコメント、整形（Prettier など）、短い関数やコンポーネントを心がけ、可読性の高いコードを維持します。

## 2. Firebase および Firestore の利用規約

### 2.1. Firebase 設定変数 (`lib/firebase.ts`)

`lib/firebase.ts` で定義される `isFirebaseConfigured` および `isDemoMode` は、**boolean 型の定数**として扱います。関数として呼び出すことは禁止します。

*   **`isFirebaseConfigured`**: Firebase の設定が完了しているかを示す boolean 値。
    *   `if (isFirebaseConfigured)` のように、直接 boolean 値として参照します。
    *   `isFirebaseConfigured()` のような関数呼び出しは禁止します。
*   **`isDemoMode`**: アプリケーションがデモモードで動作しているかを示す boolean 値。
    *   `if (isDemoMode)` のように、直接 boolean 値として参照します。
    *   `isDemoMode()` のような関数呼び出しは禁止します。

### 2.2. Firestore クエリとインデックス

Firestore のクエリは、パフォーマンスとスケーラビリティを考慮して記述します。

*   **複合インデックスの必要性**: `where()` 句と `orderBy()` 句を組み合わせる場合、または複数の `where()` 句を使用する場合は、**複合インデックスが必要になる可能性が高い**ことを常に意識します。
    *   インデックスエラーが発生した場合は、Firebase コンソールで必要な複合インデックスを作成します。
    *   開発中は、エラーメッセージに表示されるURLからインデックスを自動生成することを推奨します。
*   **データ型の一貫性**: Firestore に保存するデータの型は、`types/firestore.ts` で定義された型と厳密に一致させます。特に、`undefined` や関数などの不正なデータ型をフィールド値として保存しないように注意します。
*   **リアルタイムリスナーの管理**: `onSnapshot` を使用する際は、コンポーネントのアンマウント時に必ず `unsubscribe` 関数を呼び出し、メモリリークを防ぎます。

### 2.3. データ操作 (`lib/firestore.ts`)

`lib/firestore.ts` は、Firestore のデータ操作に関する中心的なロジックを格納します。CRUD (Create, Read, Update, Delete) 操作は、このファイルに集約します。

*   **関数の重複禁止**: 同じ名前の関数が複数定義されることを厳しく禁止します。特に、`export const` で定義される関数は一意である必要があります。
*   **エラーハンドリング**: Firestore 操作には必ず `try-catch` ブロックを導入し、エラーが発生した際には適切にログを記録し、ユーザーにフィードバックを提供します。

## 3. 認証とユーザー管理 (`contexts/auth-context.tsx`, `lib/firebase-auth.ts`)

### 3.1. `AuthContext` の利用

`contexts/auth-context.tsx` で定義される `AuthContext` は、アプリケーション全体で認証状態とユーザー情報を共有するための唯一の手段です。

*   **`AuthContextType`**: 認証コンテキストで提供されるデータの型は、`AuthContextType` インターフェースで厳密に定義します。新しいプロパティを追加する場合は、このインターフェースも更新します。
*   **`storeId` の管理**: ログイン中の店舗ID (`storeId`) は、`AuthContext` の `value` に含め、`useAuth()` フックを通じて取得します。`storeId` が `null` または `undefined` の場合のフォールバック処理を適切に実装します。

### 3.2. 認証処理

`lib/firebase-auth.ts` は、Firebase Authentication の低レベルな操作をカプセル化します。認証ロジックはここに集約し、他のファイルからはこのファイルで定義された関数を呼び出します。

## 4. コンポーネントとルーティング (`app/`, `components/`)

*   **責務の分離**: コンポーネントは単一の責務を持つように設計します。UIの表示ロジックとビジネスロジック（データ取得、状態管理）を明確に分離します。
*   **再利用性**: 共通して利用されるUI要素は `components/` ディレクトリに配置し、再利用可能なコンポーネントとして設計します。
*   **エラー境界**: 予期しないエラーが発生した場合にアプリケーション全体がクラッシュしないよう、適切な箇所にエラー境界 (Error Boundary) を設定します。

## 5. 開発ワークフロー

*   **小さく変更、即ビルド**: 新しい機能を追加したり、既存のコードを修正したりする際は、一度に大量の変更を加えるのではなく、小さな単位で変更を行い、その都度ビルドと基本的な動作確認を行います。
*   **差分（Diff）の確認**: Git でコミットする前に、`git diff` コマンドやIDEの機能を使って、変更内容を必ず確認します。特に、意図しないコードの削除や変更がないか注意します。
*   **テストの活用**: 主要な機能にはテストコードを記述し、変更後にテストを実行して回帰バグがないことを確認します。

このガイドラインは、プロジェクトの成長とともに進化する可能性があります。疑問点や改善提案があれば、積極的に議論し、より良い開発環境を構築していきましょう。
